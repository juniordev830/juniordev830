## observability-platform

[Repositório](https://github.com/juniordev830/observability-platform) · [README](https://github.com/juniordev830/observability-platform/blob/main/README.md) · blob `ae45df3e5492`

### Propósito declarado
Serviço de observabilidade **local** em Python 3.12, sem dependências externas.
A biblioteca mantém compatibilidade com os endpoints originais e adiciona
métricas Prometheus, janelas deslizantes, SLOs, alertas, incidentes e diagnósticos JSON.

> **Escopo:** demonstração de engenharia de software e testes. Não é um produto
> de monitoramento distribuído nem um substituto para Prometheus/Grafana.

### Detalhes técnicos documentados
**Executar**

Requer Python 3.10 ou superior (CI: 3.12).

~~~bash
python server.py
~~~

O servidor escuta **somente em 127.0.0.1:9091** por padrão.
Para testes automatizados, a porta 0 escolhe uma porta local livre.

**Testes**

~~~bash
python -m compileall -q .
python -m unittest discover -s tests -v
~~~

Os testes incluem compatibilidade de /health, /ready, /metrics, HEAD,
erros HTTP, contadores concorrentes, labels escapadas, cardinalidade, histogramas,
percentis, retenção de eventos, falhas de dependências, SLOs, silenciamento,
máquina de estados de alertas e ciclo de vida de incidentes.

**Segurança, limites e evolução**

- **Não exponha a porta na internet** sem autenticação, TLS, limitação de taxa e
  proteção de rede. A configuração padrão é loopback.
- Não armazene segredos ou dados pessoais em labels, mensagens ou incidentes.
- Os armazenamentos são locais, limitados e voláteis; reiniciar perde o estado.
- Health checks são síncronos; callbacks lentos podem atrasar a resposta.
- Não há agregação entre processos, persistência, tracing distribuído nem
  garantias de entrega de alertas. Futuras integrações podem incluir
  OpenTelemetry, Prometheus, Grafana e um armazenamento durável.

Projeto mantido em https://github.com/juniordev830.

### Propósito declarado
Microsserviço demonstrativo para estudo de desenvolvimento backend com Java e Spring Boot. O projeto implementa uma API REST inicial para registrar e consultar pagamentos em banco H2, com persistência via Spring Data JPA e validação de entrada.

 > **Aviso:** este é um projeto de portfólio, não um sistema de pagamentos pronto para produção. Não movimenta dinheiro nem se integra a adquirentes ou gateways reais. Não envie dados de cartão ou informações financeiras reais.

### Detalhes técnicos documentados
**Limites de segurança e acesso**

A API exige tokens de serviço distintos para leitura e administração; veja [configuração de acesso](#acesso-aos-pagamentos). Apenas `GET /api/pagamentos/status` é público. O filtro exige autenticação por padrão em todas as demais requisições, inclusive rotas desconhecidas e variações de URL, evitando depender da interpretação do caminho bruto como fronteira de segurança. Ele também funciona quando a aplicação utiliza um context path.

A listagem é paginada (padrão: 20; máximo: 50 registros). Os tokens não representam usuários e não isolam pagamentos por proprietário: qualquer portador de um token de leitura ou administração pode consultar todos os registros demonstrativos. O serviço continua limitado a `127.0.0.1`. Antes de qualquer exposição remota, faltam identidade por usuário, autorização por recurso, auditoria, TLS e configuração de produção.
